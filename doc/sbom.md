# SBOM

Status: implemented

Software bills of materials for RZI and for firmware built on it, aligned
with the EU Cyber Resilience Act (CRA) and BSI TR-03183-2: SPDX 3.0.1 (with
CycloneDX 1.6 for the module), file hashes, licenses and copyrights from
REUSE, CPE / PURL identifiers, and NTIA / CISA minimum elements checked in
CI.

See also: [security.md](./security.md), [ci.md](./ci.md),
[west-patch.md](./west-patch.md), [coding-standards.md](./coding-standards.md).

RZI produces two kinds of SBOM:

| SBOM | Describes | Generated by |
|---|---|---|
| Module SBOM | RZI at one commit and the projects pinned in `west.yml` | `scripts/generate-sbom.sh` |
| Firmware SBOM | What was compiled into one image of one build | `west spdx` via `scripts/generate-firmware-sbom.py` |

A customer importing RZI uses the module SBOM. A product shipping firmware
must ship the firmware SBOM of that exact build: only it shows which files
of Zephyr, RZI, USP, and the HALs were linked, so a CVE in a module that is
in the workspace but not in the image can be scoped out.

Neither SBOM is committed. CI generates both on every push and uploads them
as artifacts; a release attaches them to the GitHub Release next to the
images (see [Releases](#releases)).

## Module SBOM

```bash
scripts/generate-sbom.sh                # HEAD; refuses uncommitted changes
scripts/generate-sbom.sh --allow-dirty  # staged and modified tracked files
```

| File in `build/sbom/` | Contents |
|---|---|
| `rzi-<version>-src.tar.gz` | `git archive` of the described tree |
| `rzi.spdx.jsonld` | SPDX 3.0.1 JSON-LD, profiles core, software, simpleLicensing |
| `rzi.cdx.json` | CycloneDX 1.6 JSON |

What it records:

| Element | Source |
|---|---|
| RZI version | `RZI_VERSION_STRING` in `include/rzi/version.h` |
| RZI CPE / PURL | `security.external-references` in `zephyr/module.yml` |
| Source archive hash | SHA-256 and SHA-512 of the archive above |
| Every tracked file | Path, SHA-256, license and copyright from REUSE |
| Dependencies | `zephyr`, `usp_zephyr`, `usp` from `west.yml`, with the tag in the revision comment as version, PURL, SWHID of the pinned commit, and the Zephyr CPE |
| Patches | `zephyr/patches.yml`: SPDX `patchedBy` relationships to the patch files, CycloneDX `pedigree.patches` |
| Generation context | SPDX `software_sbomType: source`, CycloneDX lifecycle `pre-build` |

A `west.yml` project without an entry in `WEST_PROJECT_META` in
`scripts/generate-sbom.py` fails the run, so a new dependency cannot enter
without a supplier and license. `SOURCE_DATE_EPOCH` fixes the creation time.

Recorded components today:

| Component | Version | License | Supplier |
|---|---|---|---|
| `rzi` | `RZI_VERSION_STRING` | Apache-2.0 | RAKwireless |
| `zephyr` | revision RZI is validated against | Apache-2.0 | The Zephyr Project |
| `usp_zephyr` | `west.yml` (RZI west patches applied) | BSD-3-Clause-Clear | Semtech Corporation |
| `usp` | `west.yml` (RZI west patches applied) | BSD-3-Clause-Clear | Semtech Corporation |

An application manifest that pins its own Zephyr replaces the `zephyr`
entry; the firmware SBOM then records the Zephyr actually used.

## Firmware SBOM

Every image must be built with `CONFIG_BUILD_OUTPUT_META=y`. With sysbuild,
pass it to MCUboot too:

```sh
west build -b rzi_rak4631/nrf52840 --sysbuild rzi/samples/at -d build/at -- \
    -DCONFIG_BUILD_OUTPUT_META=y -Dmcuboot_CONFIG_BUILD_OUTPUT_META=y
python3 rzi/scripts/generate-firmware-sbom.py build/at
```

A product may set `CONFIG_BUILD_OUTPUT_META=y` in its `prj.conf` and
`sysbuild/mcuboot.conf` instead. The script refuses a build where an image
lacks it.

`build/at/spdx/<image>/` then holds, for each image (`at`, `mcuboot`):

| File | Contents |
|---|---|
| `app.jsonld` | Application sources |
| `zephyr.jsonld` | Files of each west module that were compiled, with hashes, licenses, copyrights |
| `build.jsonld` | Build profile: CMake targets, inputs, outputs, tools, flags |
| `modules-deps.jsonld` | One reference package per west module, with CPE / PURL from `module.yml` |
| `image.jsonld` | Build-type SBOM whose root elements are the flashed files (`zephyr.hex`, `zephyr.signed.bin`, ...) with SHA-256 and SHA-512, generated from `zephyr.elf` |

`image.jsonld` is written by `generate-firmware-sbom.py`, not by `west spdx`:
it adds the generation context and the SHA-512 image hashes `west spdx` does
not emit yet. Validate an image's documents together:

```sh
spdx3-validate $(for f in build/at/spdx/at/*.jsonld; do echo -j "$f"; done)
python3 rzi/scripts/check-sbom.py --strict build/at/spdx/at/*.jsonld
```

The documents can be explored with the SPDX 3 visualizer at
<https://kartben.github.io/spdx3_viz> (client-side, nothing uploaded),
including the impact view that answers whether a CVE's files are in
`zephyr.elf`.

### Licenses in the firmware SBOM

`west spdx` reads license and copyright through REUSE, per module:

- RZI: every file carries `SPDX-FileCopyrightText` and
  `SPDX-License-Identifier`; `REUSE.toml` covers the rest. CI runs
  `reuse lint`.
- USP and usp_zephyr: Semtech sources carry the Clear BSD text without SPDX
  tags. The west patches `usp/0004-reuse-license-annotations.patch` and
  `usp_zephyr/0007-reuse-license-annotations.patch` add a `REUSE.toml` to
  each module. Two third-party files in USP have license texts with no
  exact SPDX License List match and are tagged
  `LicenseRef-Brian-Gladman-AES` (`aes.c` / `aes.h`) and
  `LicenseRef-Casado-Tsigas-CMAC` (`cmac.c` / `cmac.h`); the texts are in
  USP's `LICENSES.txt`.

## Minimum elements

`scripts/check-sbom.py` checks SPDX 3 and CycloneDX documents against the
NTIA minimum elements and the CISA 2025 additions:

| Element | SPDX 3 | CycloneDX |
|---|---|---|
| SBOM author | `CreationInfo.createdBy` | `metadata.authors` |
| Tool | `CreationInfo.createdUsing` | `metadata.tools` |
| Timestamp | `CreationInfo.created` | `metadata.timestamp` |
| Generation context | `software_Sbom.software_sbomType` | `metadata.lifecycles` |
| Component name, version | `name`, `software_packageVersion` | `name`, `version` |
| Producer | `suppliedBy` | `supplier` |
| Identifier | CPE, PURL, or SWHID | `cpe`, `purl`, or `swhid` |
| Hash | `verifiedUsing`, SWHID, or hashes on every contained file | `hashes` or `swhid` |
| License | `hasDeclaredLicense` / `hasConcludedLicense` | `licenses` |
| Dependency | `dependsOn` / `contains` | `dependencies` |

For `west spdx` output, the component is each module's source package that
contains compiled files; it inherits CPE / PURL and license from the
module's reference package. Modules that contributed no files are not in
the image and are skipped. CycloneDX documents are also validated against
the 1.6 schema. CI runs the check with `--strict`.

## Releases

`.github/workflows/release.yml` runs on a `v<version>` tag that matches
`RZI_VERSION_STRING`. It builds the release images with build metadata,
generates and validates their SBOMs, generates the module SBOM, and creates
a GitHub Release with:

- `rzi-v<version>-<sample>-<board>.tar.gz`: merged and signed images, ELF
  files, and `spdx/<image>/*.jsonld`
- `rzi.spdx.jsonld`, `rzi.cdx.json`, `rzi-<version>-src.tar.gz`
- `SHA256SUMS`, `SHA512SUMS` for every asset

Release images: `samples/at` on RAK4631 and RAK3362, and
`samples/lorawan/periodical_uplink` on RAK4631, RAK3362, and RAK3372.

## Version bumps

`RZI_VERSION_STRING`, `PROJECT_NUMBER` in `doc/Doxyfile`, and the CPE / PURL
in `zephyr/module.yml` must change together; the Compliance job checks it.
When a `west.yml` revision changes, update the tag in its trailing comment
(`revision: <sha> # v1.2.1`); the SBOM takes the version from it.
